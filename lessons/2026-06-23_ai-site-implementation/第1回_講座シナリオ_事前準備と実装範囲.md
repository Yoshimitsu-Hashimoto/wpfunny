# 第1回 講座シナリオ ｜ 事前準備 & ライブ実装範囲

ペットシッター・マッチングサイト 実装編｜AIで設計をコードに落とす

---

## この回の到達点

飼い主がシッターを「探して・絞り込んで・評価順に並べて・詳細を見る」という**閲覧体験が完全に動く**。
ただし評価の数字とレビューは中身がスタブ（偽物）。本物の評価機能は第2回で接続する。

- ライブで縦に通すのは **シッター一覧（archive-sitter）と詳細（single-sitter）の2枚**
- 軸は「設計→プラン→チェック→実装」のループと、**人間がどこで判断するか**
- スタブ／ドライバーの考え方 = 「読む側を先に作る。書く側は契約（post_meta）を信じて後付けする」

---

## A. 事前準備（ライブ開始時点で完成させておくもの）

準備は「全回で使い回すもの」と「第1回だけのために下ごしらえするもの」を分けて考える。
カスタム系は **sitter 系だけ** に絞る（pet_request・独自テーブルは第1回では作らない）。

### A-0. 環境

1. Local または Studio で WordPress 環境を構築
2. クラシックテーマの土台を用意
3. プラグインは **ACF（無料版）のみ**。CF7・WP Mail SMTP 等は第1回では不要

### A-1. 静的モック（全ページ分・共通デザイン）※全回で使い回す資産

- 一覧・詳細・依頼一覧・依頼詳細・各フォーム・法的ページまで、**一貫したトンマナで全ページ作っておく**
- ただしライブで出すのは「その回で作るページ」だけ。残りは手元に伏せておく（ネタバレ回避）
- 同時に色・フォント・余白の基準を決め、style.css とヘッダー／フッター（header.php / footer.php）の共通基盤に反映しておく

### A-2. sitter 系カスタムレイヤーの登録

設計書 5.2 / 5.3 / 5.5 をそのまま実装する。**事前にコード生成 → 動作確認まで済ませておく**。

- CPT `sitter`（supports: title, editor, thumbnail, author ／ public: true ／ has_archive: `/sitters/`）
- タクソノミー `animal_type`（犬・猫・小動物・鳥・爬虫類）、`area`（東京都・神奈川県・埼玉県…）→ ターム作成まで
- ACF フィールドグループ（sitter に紐付け）
  - `sitter_price`（number）
  - `sitter_has_license`（true_false）
  - `sitter_available_hours`（text）
  - `sitter_animal_license`（radio：有／無）
  - `sitter_animal_license_no`（text・条件付き表示）
  - `rating_average`（number）← **第1回はスタブ手入力。第2回でシステム更新＋ロック**
  - `rating_count`（number）← 同上

### A-3. ダミーシッターの投入（6人ほど）

各シッターに以下をセット。**rating_average は意図的にバラす**（4.2 / 4.8 / 3.9 / 4.5 …）と並べ替えの動作が映える。

- タイトル（名前）／アイキャッチ（プロフィール写真）／本文（自己紹介）
- ACF 各値（料金・資格・対応時間帯・登録番号）
- `rating_average`・`rating_count`（スタブ手入力）
- `animal_type`・`area` のタームを割り当て

> 準備の速さなら WP-CLI 一括投入（`wp post meta update <id> rating_average 4.5`）。
> ただし**ライブで1〜2人ぶんは管理画面から手入力する様子をあえて見せる**と「スタブを手で埋めている」感が伝わる。

### A-4. 共通基盤の確定

- style.css（色・フォント・余白）と header.php / footer.php を全ページ共通の枠として固める
- 各回の WordPress 化が「get_header() / get_footer() の枠に中身のテンプレートを差し込むだけ」になる状態にしておく

### A-5. スナップショット取得

- 「Phase 1 完了・独自テーブルなし」の状態でスナップショットを取る（ライブ用の初期状態）
- ゴールデンパス（後述のライブ手順）を一度自分で通し、効いたプロンプトと出力を全部保存（事故時の差し替え用）
- 別途「全部入り（完成形）」のスナップショットも用意しておくと、回の最後に完成イメージを見せる時に使える

## B. ライブ実装（この回でその場でやること）

ライブで触るのは A で作った土台の**上に乗るテンプレートとクエリの層だけ**。

### Step 1. 設計書を読み込ませる

AI に設計書を「唯一の正」として読ませる。以降の判断はすべてここを根拠にする。

### Step 2. 今日のモックを提示

一覧・詳細のモックだけ出す。「今日はこの見た目を WordPress で動くようにする」とゴールを共有。

### Step 3. 要素プランを作らせる（→ サンプルプロンプト ⑤）

設計書から「一覧・詳細を作るのに必要なもの」を AI に洗い出させる。

### Step 4. プランを人間がチェック ★最大の見せ場

- **仕分け**：プランには CPT・ACF 登録まで含まれてくる。「ここは下ごしらえ済み。今日はテンプレートとクエリだけ」と線を引く
- **集計方式**：評価順の並べ替えで AI は「レビューを毎回 AVG 集計」を提案しがち → 設計書のキャッシュ方式（post_meta を読むだけ）に正す

### Step 5. 一覧テンプレートを実装（→ サンプルプロンプト ⑥）

`archive-sitter.php`。tax_query 絞り込み、meta orderby 並べ替え、ページネーション。

- ★見せ場：AI が `wp_pet_reviews` を集計するコードを書く → **そのテーブルは存在しないので落ちる** → 設計どおり `rating_average` を読むコードに直すと動く。「賢そうな提案が壊れて、設計に従った実装が動く」を実演

### Step 6. 詳細テンプレートを実装（→ サンプルプロンプト ⑦）

`single-sitter.php`。ACF 各値の表示、評価平均・件数の表示、問い合わせボタン。

- ★見せ場①：`rating_average` を表示する時「これは手入力のスタブ。本来システムが書く欄なので、最終的には手入力できないようロックする。それは次回」と**明示的に宣言**（第2回への伏線）
- ★見せ場②：個別レビュー一覧は `wp_pet_reviews` 由来 → テーブルがまだ無いので**プレースホルダ表示**にする（「レビュー一覧は次回実装」）。これも第2回の接続点
- 問い合わせボタンのリンク先（フォーム）は未実装 → 「導線だけ置いて中身は後の回」と扱う

### Step 7. 動作確認

絞り込み（動物・エリア）、並べ替え（料金昇順・降順、評価降順）、ページネーション、URL パラメータ（`?animal_type=dog&area=tokyo&orderby=price&order=asc`）を一通り。

### Step 8. まとめ & 次回予告

- 今日作ったもの＝「読む側」。動いているが評価とレビューはスタブ
- 次回＝「書く側」を作ってスタブを本物に差し替える。**一覧側のコードは1行も変えずに結合できる**ことが次回のクライマックス、と予告

## C. 第1回で「やらない」こと（混ぜないための明示リスト）

pet_request の CPT・ACF ／ 独自テーブル2種（inquiries・reviews）／ 各種フォーム ／ メール認証・トークン ／ WP Cron ／ 管理画面カスタムページ ／ 法的ページの WordPress 化。
→ すべて第2回・第3回でその回の下ごしらえとして順次。

## D. サンプルプロンプト集

> いずれも「設計書を読み込ませた状態」が前提。`設計書.md` は統合済みの要件定義書兼設計書を指す。

### D-1. 事前準備用プロンプト

#### ① モック生成（A-1 用）

```
添付の設計書を読んでください。これはペットシッター・マッチングサイトの要件定義書です。

この設計に基づいて、サイト全体の静的モックを HTML/CSS で作ってください。条件は以下です。

- 対象ページ：シッター一覧、シッター詳細、依頼一覧、依頼詳細、依頼投稿フォーム、
  シッター登録フォーム、評価フォーム、法的3ページ（特商法・PP・利用規約）
- 全ページで一貫したデザインシステム（配色・タイポグラフィ・余白）を使うこと
- ヘッダー・フッターは全ページ共通
- 配色とフォントの基準値を、あとで WordPress の style.css に移せる形で
  CSS 変数として冒頭にまとめて定義すること
- まずは「シッター一覧」と「シッター詳細」を優先して作り込み、
  残りは同じトンマナで揃えること

ペットを預ける安心感が伝わる、やわらかく信頼感のあるトーンでお願いします。
```

#### ② CPT・タクソノミー・ACF 登録（A-2 用）

```
このディレクトリ内の要件・設計書を読んでください。

設計書 5.2・5.3・5.5 に基づいて、シッター（sitter）まわりのデータ定義を
WordPress に登録するコードを書いてください。出力は単一のカスタムプラグイン
（例：pet-sitter-core）としてまとめてください。第2回で同じプラグインに
register_activation_hook + dbDelta() でテーブル作成を足すので、置き場所と作法を
最後まで一貫させるためにプラグイン形式で統一します。

含めるもの：
- カスタム投稿タイプ sitter
  - supports: title, editor, thumbnail, author
  - public: true / has_archive: true（アーカイブ /sitters/）
  - rewrite slug: sitters（個別 URL は /sitters/%postname%/）
- タクソノミー animal_type（sitter に紐付け・階層あり）：犬・猫・小動物・鳥・爬虫類
- タクソノミー area（sitter に紐付け・階層あり）：東京都・神奈川県・埼玉県 等
- ACF フィールドグループ（acf_add_local_field_group で sitter に紐付け・コード管理）
  - sitter_price（number）
  - sitter_has_license（true_false）
  - sitter_available_hours（text）
  - sitter_animal_license（radio：有/無）
  - sitter_animal_license_no（text・sitter_animal_license が「有」のとき条件表示）
  - rating_average（number）
  - rating_count（number）
- 上記タクソノミーの初期ターム（犬・猫… ／ 都県名）の登録も含めること

置き場所のルール（重要）：
- CPT・タクソノミー・ACF の「登録」は init / acf/init フックで毎リクエスト行う
- 初期タームの「作成」はデータの書き込みなので、register_activation_hook の中で
  有効化時に一度だけ行う（毎回作ろうとしないこと）

注意：
- rating_average / rating_count は本来システムが更新する欄です。今は手入力した値を
  使いますが、将来この欄を編集画面でロックする想定です。その旨をコメントで残して
  ください（ロック自体はまだ実装しない）。
```

> ACF をコードではなく管理画面（GUI）で作って見せたい場合は、上記から ACF 部分を外し、
> CPT・タクソノミーだけコード生成 → ACF はGUIで、という分担でもよい。

#### ③ ダミーシッター投入（A-3 用）

```
添付の設計書の sitter 定義に合わせて、デモ用のダミーシッターを6人ぶん登録する
スクリプトを作ってください（WP-CLI コマンド列、または wp eval-file で実行できる
PHP のどちらでも可）。

各シッターに設定する内容：
- タイトル（架空の名前）／本文（自己紹介の短文）
- ACF：sitter_price、sitter_has_license、sitter_available_hours、
  sitter_animal_license、sitter_animal_license_no
- post_meta：rating_average、rating_count
  ※ rating_average は6人で意図的にバラす（例 4.9 / 4.5 / 4.2 / 4.1 / 3.9 / 3.6）。
    並べ替えの動作確認に使うため。
- animal_type・area のタームを各自に割り当て（人によって対応動物・エリアを変える）

注意：
- これはスタブデータです。rating_average / rating_count は本来レビューから計算
  される値ですが、今回は固定値を手で入れます。
- アイキャッチ画像はこのスクリプトでは扱いません（別途 wp media import か管理画面
  から手動設定する前提）。その箇所はコメントで明示してください。
```

#### ④ style.css・ヘッダー／フッター（A-4 用）

```
モック生成（①）で作った静的モックの配色・タイポグラフィ・余白を、
クラシックテーマの共通基盤に落とし込みます。以下を出力してください。

- style.css：モックの配色・フォント・余白を、サイト全体の基本スタイルとして整理
  （CSS変数で冒頭にまとめてよい）。先頭にはテーマ情報のコメントヘッダーを入れること
- header.php / footer.php：全ページ共通のヘッダー・フッター
  - header.php に wp_head()、footer.php に wp_footer() を正しい位置に入れること
  - フッターには法的3ページへの常設リンクを含める（設計書 4.1）：
    特商法 /tokushoho ・プライバシーポリシー /privacy ・利用規約 /terms
- 各ページのテンプレート（archive-sitter.php 等）は get_header() / get_footer() で
  この共通部分を呼び出す前提で組むこと
```

### D-2. ライブ用プロンプト

#### ⑤ 要素プラン生成（ライブ Step 3 用）

```
添付の設計書を読んでください。

今日はこのうち「シッター一覧ページ」と「シッター詳細ページ」を WordPress で
実装します。この2ページを作るために必要な要素を、設計書を根拠に洗い出して
プランとして整理してください。次の観点で列挙してください。

- 必要なカスタム投稿タイプ・タクソノミー・カスタムフィールド
- 必要なテンプレートファイル
- 一覧の絞り込み・並べ替え・ページネーションをどう実装するか（WP_Query の設計）
- 評価平均での並べ替えを、設計書ではどのデータをどう読んで実現する想定か
- 詳細ページで表示する項目と、その取得元（投稿・ACF・post_meta・カスタムテーブル）

※実装方針は必ず設計書の記述に従ってください。一般的なベストプラクティスより
　設計書の指定を優先してください。
```

> チェックの狙い：この出力に対して人間が「①土台は下ごしらえ済みなので除外」「②評価平均は集計ではなく post_meta キャッシュを読む（設計書5.5/7.2）」を指摘する。

#### ⑥ 一覧テンプレート実装（ライブ Step 5 用）

```
設計書の 3.1 と 5〜7 に従って、シッター一覧のテンプレート archive-sitter.php を
実装してください。要件は以下です。

- 表示件数 10件・ページネーションあり
- 絞り込み：animal_type（対応動物）・area（対応エリア）を tax_query で
- 並べ替え：料金（sitter_price 昇順・降順）、評価（rating_average 降順）
- URL パラメータ例：?animal_type=dog&area=tokyo&orderby=price&order=asc
- 評価順の並べ替えは、レビューを毎回集計するのではなく、
  設計書5.5・7.2 のとおり post_meta（rating_average）のキャッシュ値を読むこと
- 添付モックの一覧デザインに合わせること
- 連絡先（メール・電話）は一覧に一切出さないこと
```

> もし AI が `wp_pet_reviews` を集計する実装を出してきたら、あえて一度動かして
> 「テーブルが無いので落ちる」を見せ、`rating_average` を読む実装に直す。

#### ⑦ 詳細テンプレート実装（ライブ Step 6 用）

```
設計書の 3.1 詳細ページ（F-02）に従って single-sitter.php を実装してください。
表示項目と取得元は次のとおりです。

- プロフィール写真：アイキャッチ
- 名前：投稿タイトル
- 自己紹介：本文
- 資格の有無：ACF sitter_has_license
- 対応時間帯：ACF sitter_available_hours
- 料金：ACF sitter_price
- 動物取扱業登録番号：ACF sitter_animal_license_no
- 評価平均・件数：post_meta（rating_average / rating_count）
- 個別レビュー一覧：※今回はテーブル未実装のため、
  「レビューは準備中」のプレースホルダ表示にしてください（次回実装）
- 「相談する」ボタン：問い合わせフォームへの導線（リンク先は仮で可）

連絡先（メール・電話）は表示しないこと。モックの詳細デザインに合わせること。
```

> 表示時に口頭で：「rating_average は今は手入力のスタブ。本来システムが書く欄なので
> 最終的には編集画面で手入力できないようロックする。それは次回やります」と宣言。

## E. 判断チェックリスト（人間が見る観点 ＝ 講座の核心）

ライブでプラン・実装をチェックする時に拾う観点。これを見せること自体が価値。

- [ ] プランに含まれる「土台（CPT・ACF登録）」と「今日作るもの（テンプレ・クエリ）」を仕分けたか
- [ ] 評価順並べ替えが「毎回集計」になっていないか（post_meta キャッシュを読んでいるか）
- [ ] 存在しないテーブル（wp_pet_reviews）を参照していないか
- [ ] rating_average を「スタブである」と受講者に明示したか（次回ロックの予告も）
- [ ] 個別レビュー表示をプレースホルダにし、次回への接続点として説明したか
- [ ] 連絡先がフロントに漏れていないか（設計書の非表示要件）
- [ ] 問い合わせボタンの導線だけ置き、フォーム本体は今回作らないと線引きしたか

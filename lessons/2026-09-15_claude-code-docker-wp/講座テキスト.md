## 今日の軸

> **Local は GUI で「人が」操作する道具。**
> **Docker はコマンドで「機械が」操作する道具。**
>
> だから AI に任せられる範囲が段違いになる。

今日はこれを、実際に手を動かして確かめます。

## 前提の構成

案件ごとに1フォルダ。その親に、共通のルールを1枚置いてあります。

```

├── CLAUDE.md

└── demo/                  ← 今日作る子。この中で作業する
    └── CLAUDE.md          ← この環境だけの情報（ポート番号など）
```

# STEP 1｜フォルダを作って `claude` を起動する

やるのは、**フォルダを作って、その中で `claude` と打つ**。それだけです。

```bash
cd /Users/yoshio/work/wp-local
./scripts/new-env.sh demo 8080
cd demo
ls -a
```

`ls -a` の結果 —— **`CLAUDE.md` が1枚だけ**。

compose.yml もありません。この空っぽの状態から作らせます。

```bash
claude
```

起動すると、Claude Code は**親と子の `CLAUDE.md` を両方読み込んだ状態**になります。
これが後で効いてきます。

# STEP 2｜WordPress 環境を一発で作らせる

**作りたいものだけ書きます。どう作るかは書きません。**

### プロンプト ①

```
このディレクトリに WordPress のローカル環境を作って、ブラウザで開ける状態まで持っていってください。
compose.yml と Dockerfile と .env を作り、コンテナを起動し、WordPress の初期セットアップまで
終わらせてください。終わったらアクセス先の URL と管理者ログイン情報を教えてください。
```

### 裏で起きていること（2〜4分）

1. `compose.yml` / `Dockerfile` / `.env` を生成
2. `docker compose up -d --build` —— コンテナを2つ起動（WordPress と MySQL）
3. `wp core install` —— WordPress の初期セットアップ
4. `wp language core install ja --activate` —— 日本語化
5. URL とログイン情報を日本語で返す

### ここで気づいてほしいこと

指定していないものを数えてみてください。

- ポート番号 → 指定していない
- 管理者ID・パスワード → 指定していない
- イメージのバージョン → 指定していない
- サイト名 → 指定していない

**それでも全部決まりました。** なぜかは STEP 3 で明かします。

> ここまで、**人が一度もクリックしていません。**
> Local なら今、新規サイト作成ウィザードを3〜4画面クリックしているところです。

# STEP 3｜ブラウザで開く／ルールの正体を見る

### 開く

```
http://localhost:8080            サイト
http://localhost:8080/wp-admin   管理画面（admin / password）
```

日本語の WordPress が立ち上がっています。

### さっきのプロンプト、3行でしたよね

なぜあれで足りたのか。答えは親の `CLAUDE.md` です。

```
wp-local/CLAUDE.md
```

ここに、こういうことが書いてあります。

| 書いてあること | 中身 |
|---|---|
| ポート割当 | `8080` から順に払い出す |
| イメージ | タグを固定する（`latest` は使わない） |
| 管理者 | `admin` / `password` |
| WP-CLI | `docker compose exec wordpress wp` 経由で使う |
| 確認の要否 | 削除以外は聞かずに実行してよい |

### 今日いちばん持ち帰ってほしい考え方

> **「何を作るか」はプロンプトに。**
> **「どう振る舞うか」は CLAUDE.md に。**

一度書けば、次の案件からはこのファイルごと使い回せます。
プロンプトが短くて済むのは、ルールを別の場所に置いてあるからです。

# STEP 4｜環境の中身を会話で確認する

ここからは環境を触ります。まずは**見るだけ**。

### プロンプト ②

```
この WordPress に今どんなユーザーがいるか教えてください。あと投稿は何件ありますか。
```

### 返ってくるもの（30〜60秒）

> 管理者1名（admin）、投稿は1件（Hello world!）です

裏では WP-CLI がこう動いています。

```bash
docker compose exec wordpress wp user list
docker compose exec wordpress wp post list --format=count
```

### ここで気づいてほしいこと

今のは管理画面で言えば「ユーザー一覧」と「投稿一覧」を開く操作です。

でも **画面のどこにあるかを知らなくていい**。日本語で聞いただけです。

# STEP 5｜ダミー記事を10件作らせる

次は書き込みます。制作でよくあるやつです —— 表示確認用に記事が10件ほしい。

### プロンプト ③

```
表示確認用に、ブログっぽいダミー記事を10件作ってください。
カテゴリを3つ作って振り分け、本文も200文字程度でそれらしく書いてください。公開状態にしてください。
```

### 返ってくるもの（1〜3分）

カテゴリ3つと記事10件。**本文まで書かれています。**
Lorem ipsum ではなく、読める日本語です。

### ここで気づいてほしいこと

これを管理画面でやると、10回ぶんこれを繰り返します。

```
新規追加 → タイトル入力 → 本文入力 → カテゴリ選択 → 公開
```

10件で今2分。**100件でも同じプロンプトです。**

> ここが Local との決定的な差。
> GUI は人の手の速度で頭打ちになる。コマンドは件数が変わっても手間が変わらない。

# STEP 6｜作ったものを会話で確かめる

作ったものを、また会話で確認します。

### プロンプト ④

```
今ある記事のうち一番本文が長いものを探して、内容を3行で要約してください。
```

### プロンプト ⑤

```
編集者権限のユーザーを1人追加して、今のユーザー一覧を見せてください。
```

### 答え合わせ

ブラウザに戻って**リロード**（⌘ + Shift + R）。

- 投稿一覧に10件
- ユーザー一覧に `editor01`

会話でやったことが、ちゃんと WordPress に反映されています。

### 今日の結論

> 今やったことは全部、**管理画面のどこかを開く操作に相当します。**
> ユーザー追加も、記事作成も、一覧の確認も。
>
> コマンドがあるから、それを会話にできた。
> **これが Docker を使う一番の理由です。**

# AI に任せきれない場面

正直な話もしておきます。全部が速くなるわけではありません。

### 1. 表示崩れは伝わらない

「CSSが崩れてる」と言っても AI には**見えていません**。
スクリーンショットを撮って渡す必要があります。目で見る仕事は残ります。

### 2. 初回のダウンロードは待つ

イメージの取得は素の状態だと3〜5分かかります。これは AI では縮まりません。

### 3. ポートの管理は人がやる

8080 が埋まっていると起動しません。
AI は「ポートを変えていいですか」と聞いてはくれますが、
**どのポートが空いているかを知っているのは人だけ**です。
`projects.md` で表を管理しているのはこのためです。

> AI は速い。
> けれど、**目で見ること・待つこと・番号を管理すること**は人の仕事として残ります。
